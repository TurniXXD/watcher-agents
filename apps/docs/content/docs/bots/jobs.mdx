`jobs-bot` owns collection, scheduling, matching, notifications, source controls,
candidate-profile settings, and application tracking through its authorized
Telegram surface. It runs at 08:00, 12:00, and 19:00 in `Europe/Prague` with
persisted, daylight-saving-aware schedules.

## Commands

| Command                                   | What it does                                                      |
| ----------------------------------------- | ----------------------------------------------------------------- |
| `/start`                                  | Opens the bot without changing settings or starting collection.   |
| `/help`                                   | Shows commands, syntax, statuses, and examples.                   |
| `/about`                                  | Explains matching, data ownership, automation, and limits.        |
| `/jobs_run [all\|SOURCE_ID] [dry]`        | Runs enabled/all or one source; `dry` prevents writes and alerts. |
| `/jobs_status`                            | Shows scheduler and source health.                                |
| `/jobs_sources`                           | Lists implemented sources and disabled reasons.                   |
| `/jobs_latest`                            | Lists recent scored vacancies and IDs.                            |
| `/jobs_show JOB_ID`                       | Shows source evidence, evaluation, and application notes.         |
| `/jobs_search QUERY`                      | Searches stored title/company text.                               |
| `/jobs_applications [STATUS]`             | Lists the private application pipeline.                           |
| `/jobs_source SOURCE_ID on\|off`          | Enables or disables a supported source.                           |
| `/jobs_mark JOB_ID STATUS`                | Sets the application status.                                      |
| `/jobs_note JOB_ID NOTE`                  | Adds a private note.                                              |
| `/jobs_followup JOB_ID YYYY-MM-DD\|clear` | Sets or clears a follow-up date.                                  |
| `/jobs_profile [COMPLETE_JSON]`           | Shows or replaces the validated candidate profile.                |
| `/jobs_reevaluate`                        | Re-scores stored jobs after profile changes.                      |

## Collection contract

Listing discovery uses conditional HTTP requests, timeouts, bounded retries,
`Retry-After`, stable source IDs, and per-source failure isolation. A detail
endpoint is called only for a new listing, a changed listing hash, or after the
72-hour refresh interval. Raw observations and canonical jobs are separate;
company, normalized title, and location form the conservative cross-source
fingerprint while every source URL is preserved.

Before a new matching alert is reserved, the exact application URL receives a
bounded public-URL check even when it uses the same hostname as the listing.
Confirmed closed links are neither alerted nor included in `/jobs_latest`.
Scheduled runs additionally revalidate up to 25 stale matching links per run,
five at a time, with a 24-hour freshness window. Explicit application controls
confirm an open job; HTTP 404/410 and closure text such as Greenhouse's “no
longer open” response confirm closure. Inconclusive or failed checks remain
unverified/unknown, and redirect targets are revalidated against the SSRF
policy.

Enabled global sources are the separate Remote Frontend and Remote Backend
public API boards, Himalayas RSS, Startup Jobs engineering RSS,
RemoteFirstJobs RSS, Remote OK's public API, StartupJobs.cz's official
active-offers sitemap with standardized `schema.org/JobPosting` detail data,
and Agoda's fixed public Greenhouse board.
StartupJobs.cz detail requests are limited to 30 per minute and run only for
new, changed, or 72-hour-stale listings. Configured tenant identifiers
also enable Greenhouse, Lever, Ashby, SmartRecruiters, Workable, Recruitee, and
Teamtailor adapters; an empty list keeps that ATS source unavailable rather than
guessing company identifiers. DeveloperJobs.ch, CoolJobs.eu, Práce za rohem,
and LinkedIn remain explicit disabled registry records because
no verified permitted public job-seeker feed is configured. The worker never
automates logged-in pages or bypasses access controls.

## Eligibility and alerts

Mandatory university degrees, unqualified Computer Science or related
bachelor/BS/BSc/BCS requirements, every mandatory language other than English,
Staff engineering titles, experience requirements above the five-year profile,
graduate-only eligibility, incompatible country-only restrictions, and
unrelated roles are hard blockers. Foreign onsite and hybrid roles remain
eligible when they do not require residence in an incompatible country and
English is sufficient. Preferred degrees and degree-or-equivalent-experience
wording are not blocked. Ambiguous location, authorization, or fluent-English
requirements are marked `UNCERTAIN`. The deterministic 100-point score reports
matched skills, gaps, blockers, uncertainties, and its weighted breakdown.

The default profile requires evidence of Next.js, React.js, Node.js, or
TypeScript for engineering vacancies and rejects roles centered on PHP, Java,
C++, Go, .NET, or Svelte. Explicit adjacent paths remain eligible without a
target-stack keyword: Forward Deployed Engineer, Forward Deployed Project
Manager, Technical Project/Program Manager, Implementation Engineer, and
Solutions Engineer. Digests and `/jobs_latest` are ordered from highest to
lowest match score.

The first import is baseline-only. Later runs reserve one immutable initial
digest key per canonical job, so neither a second source nor a changed listing
can silently re-alert it. Telegram is primary; an optional HTTP e-mail gateway
receives the same digest payload.

When `NOTION_API_KEY` and `JOBS_NOTION_DATA_SOURCE_ID` are configured together,
every evaluated vacancy is mirrored to Notion, including ineligible rows and
their blocker evidence. Existing evaluated jobs are backfilled on startup.
Persisted local sync claims and `Watcher Job ID` lookup make retries idempotent;
Notion failures are retained for retry and never cancel a source run. PostgreSQL
remains authoritative and Notion edits are not imported back.

The default profile contains the supplied CV facts and records end-client work
separately from its `via` agency. Optional OpenAI-compatible evaluation works
with local Ollama, validates structured output with Zod, contributes only a
bounded portion of the score, and can never remove deterministic hard blockers.
Failures fall back to deterministic scoring. Evaluation metadata and token usage
are cached by profile version and content hash.

## Telegram controls and deployment

The private Telegram commands expose manual and dry runs, latest scored jobs,
source enable/disable controls, application states, private notes, and validated
candidate-profile JSON editing. The bot never applies or contacts employers;
those actions remain manual. Production runs only the `jobs-bot` service and
keeps its readiness endpoint private on port `4090`.
