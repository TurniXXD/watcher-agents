## Overview

The Vantuch Content Hub (`apps/content-cms`) is a Payload CMS 3 application on
Next.js. It is the single source of truth for editorial and published content
on vantuch.dev. Bots submit events, articles, news, publications, and social
post drafts through an authenticated ingestion API; editors and reviewers
approve and publish them in the admin; the website reads a read-only public
REST API. It has no Telegram surface. It has its own image and migrations, runs as
a required `content-cms` Compose service in every release, and shares the
Watcher PostgreSQL database on `watcher-postgres`. Bots send publishable content
through its API; their operational state stays in the Watcher database.

Bot output, editorial content, and proposed bot changes are stored separately.
Identical submissions write nothing; changes to reviewed, published, or
human-edited fields become pending updates. Verified cancellations and
unconflicted date corrections are applied to live events immediately; a
conflicting date change hides the event after a configurable grace period.

## Commands

The application has no Telegram commands. Operator commands:

| Command                                                                               | Purpose                                               |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `pnpm --filter @watcher/content-cms dev`                                              | Development server on port 3100                       |
| `pnpm --filter @watcher/content-cms migrate`                                          | Apply Payload migrations                              |
| `pnpm --filter @watcher/content-cms credentials:create -- --bot <id> --scopes events` | Create a bot credential (token shown once)            |
| `pnpm --filter @watcher/content-cms openapi:export`                                   | Export OpenAPI files for `openapi-typescript`         |
| `docker compose -f docker-compose.production.yml ps content-cms`                      | Inspect the CMS after the standard Watcher deployment |

## Endpoints

| Path                                                                                         | Access                                           |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `/admin`                                                                                     | Payload login, Cloudflare Access                 |
| `/api/public/v1/events`, `/events/:slug`, `/events/featured`, `/events/categories`           | Anonymous, read-only                             |
| `/api/public/v1/articles`, `/articles/:slug`, `/news`, `/publications`                       | Anonymous, read-only                             |
| `/api/public/docs`, `/api/public/openapi.json`                                               | Anonymous                                        |
| `/api/ingest/v1/{events,articles,news,publications,social-posts}`, `/api/ingest/v1/runs/:id` | Per-bot bearer credential with scopes            |
| `/api/ingest/docs`, `/api/ingest/openapi.json`                                               | CMS login                                        |
| `/api/health`, `/api/ready`                                                                  | Anonymous, no data                               |
| `POST /api/mcp`                                                                              | Per-user MCP API key (Bearer), Cloudflare Access |

Events support `city` (default `brno`), `category`, `from`, `to` (date-only
values in Europe/Prague), `q`, `limit` (default 20, max 100), `cursor`, `sort`,
`free`, `freeFood`, and `featured`. `freeFood=true` returns only events whose
source explicitly confirms free food.

## Integrations

- **PostgreSQL** (required): Watcher database on `watcher-postgres` via `@payloadcms/db-postgres`; Payload and Prisma use separate tables and migrations.
- **RustFS** (required in production): existing S3-compatible store on the `vantuch` network via `@payloadcms/storage-s3`.
- **Brno Events Agent** (optional producer): sends events through its outbox when `CONTENT_CMS_URL` and `CONTENT_CMS_INGEST_TOKEN` are set.
- **vantuch.dev website** (optional consumer): public API, revalidation webhook, preview links.
- **MCP clients** (optional): AI assistants such as Claude Code connect to `/api/mcp` with a per-user API key created in the admin under _MCP → API Keys_.
- **Cloudflare Tunnel and Access** (production): Access protects the host except `/api/public`, `/api/media/file`, and `/api/health`.

## Safety boundaries and limitations

- Bot credentials can never publish; only approved content can be published; rejected content is never public.
- Native Payload REST endpoints require a CMS login; GraphQL is disabled.
- MCP tools act as the API key's owner with normal access control: editors can draft but not approve or publish; users, bot credentials, and ingestion logs are not exposed; nothing can be deleted over MCP.
- Source images and excerpts stay internal; only media with publication rights are public.
- Rate limits are per process (single instance). Swagger UI assets load from a pinned CDN version.
- Social platform publishing is not implemented.
