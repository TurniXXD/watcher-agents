## Overview

Maintenance Agent evaluates source health, run quality, deployment updates,
host/Ollama capacity, confirmed Trivy findings, and upstream security
intelligence. Host inspection is read-only through `/proc` and `/sys`; neither
the agent nor the scanner receives the Docker socket. It sends cooldown-aware,
deduplicated alerts and recovery messages.

## Architecture and flow

<Mermaid
  label="Maintenance evidence, finding, and notification workflow"
  chart={`flowchart LR
    A["Scheduler or /run"] --> B{"Advisory lease acquired?"}
    B -->|No| C["Skip overlapping evaluation"]
    B -->|Yes| D["Read Watcher telemetry"]
    D --> E["Read host and Ollama capacity"]
    E --> F["Apply deterministic health rules"]
    F --> G{"Finding supported now?"}
    G -->|Yes| H["Open or refresh finding"]
    G -->|No| I["Resolve stale finding"]
    H --> J["Create diagnostic recommendation"]
    J --> K["Idempotent Telegram outbox"]
    I --> K
    K --> L["Alert, recovery, daily, or weekly report"]
    J -.-> M["No automatic production change"]`}
/>

Scheduled evaluations claim a PostgreSQL advisory lease so multiple containers
cannot run the same due interval. Daily and weekly reports are placed in the
persistent Telegram outbox with per-run/per-chat idempotency and transient retry.
Recommendations are diagnostic and never apply production changes automatically.
Source freshness is based on successful requests relative to each source's own
cadence. A successful request with zero items is healthy. Likewise,
`duplicatesRemoved` measures duplicates prevented before delivery; a duplicate
output finding requires direct feedback that repeated content reached a user.
When a later evaluation no longer supports a deterministic finding, the agent
resolves it before reopening only findings backed by current evidence.

### Security intelligence flow

<Mermaid
  label="Security scanning, enrichment, and reporting flow"
  chart={`flowchart LR
    A["Hourly/on-deploy workflow"] --> B["Pinned Trivy container"]
    B --> C["Read-only lockfiles/manifests"]
    B --> D["Immutable GHCR digest"]
    C --> E["Authenticated loopback ingestion"]
    D --> E
    F["Daily/manual scheduler"] --> G["OSV package + NVD CPE watch"]
    E --> H["Confirmed environment findings"]
    G --> I["Verification-required advisories"]
    H --> J["EPSS + CISA KEV enrichment"]
    I --> J
    J --> K["Existing findings/recommendations tables"]
    K --> L["Immediate, daily, weekly outbox delivery"]
    L -.-> M["No update, restart, or shell execution"]`}
/>

Trivy normalizes Linux packages, npm dependencies, Go modules, Rust crates, and
supported misconfiguration checks. A successful complete scan moves absent
confirmed fingerprints to RESOLVED; rediscovery becomes RESURFACED. Technology
watch uses structured OSV package identities or NVD CPEs, never keyword
matching, and never claims deployment impact without installed-version evidence.
Cloudflare/Vercel managed status incidents remain provider-managed rather than
customer-patchable findings.

FIRST EPSS and CISA KEV enrich CVEs independently. Missing data stays
unavailable. Immediate alerts apply only to NEW/RESURFACED confirmed findings;
CRITICAL and CISA KEV always alert, while other findings use the configurable
risk threshold. Daily reports visibly separate confirmed impact from watch-only
advisories.

The scanner workflow's non-secret
`SECURITY_SCAN_MIN_INTERVAL_MINUTES` defaults to `360`. Its hourly wakeup scans
immediately when a lockfile hash or immutable image digest changes, otherwise it
waits until that minimum interval. The optional watchlist JSON replaces the
built-in list and must use `OSV_PACKAGE`, `NVD_CPE`, or provider-managed
`OFFICIAL_PROVIDER` entries with the corresponding structured identifier.

AI-enabled bots accept `OPENLIT_ENABLED`, `OPENLIT_ENVIRONMENT`,
`OPENLIT_SAMPLING_RATIO`, `OTEL_EXPORTER_OTLP_ENDPOINT`, and optional
`OTEL_EXPORTER_OTLP_HEADERS`. OpenLIT is disabled by default and requires an
external endpoint when enabled. Prompts/outputs are never captured; retention
and further metadata redaction are configured in that external backend.

## Execution and scheduling

```bash
pnpm --filter @watcher/maintenance-agent dev
pnpm --filter @watcher/maintenance-agent typecheck
pnpm exec vitest run apps/maintenance-agent/src/__tests__
```

The scheduler polls every 30 seconds by default. Health analysis defaults to six
hours, daily analysis to 24 hours, and weekly analysis to seven days.

## Integrations

| Source/service                             | Role                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| Watcher PostgreSQL                         | Run results, source health, delivery state, findings, and recommendations. |
| `/proc`, `/sys`, host cgroups              | Read-only CPU, memory, process, and capacity observations.                 |
| NVIDIA CLI/DRM sysfs                       | Optional GPU utilization and capacity data.                                |
| Ollama API/runtime metrics                 | Queue, request, CPU/GPU balance, and availability checks.                  |
| Trivy JSON                                 | Confirmed dependency/image vulnerabilities and misconfigurations.          |
| OSV, NVD, FIRST EPSS, CISA KEV             | Structured watch advisories and sourced exploitation/risk enrichment.      |
| External OTLP/OpenLIT backend              | Sampled, content-free Ollama traces; no backend is added to Compose.       |
| Release and maintenance changelog files    | `/updates` and deployment-version context.                                 |
| Every runnable Watcher bot/agent           | Readiness and freshness status; no cross-service mutation.                 |
| Authenticated maintenance API and Telegram | Approval records and private operator reporting.                           |

## Troubleshooting

- Duplicate reports indicate delivery/idempotency state, not necessarily two
  analyses; inspect outbox keys and scheduler ownership.
- High source duplicate counters are expected for periodic snapshot providers
  when unchanged records are filtered before analysis or delivery.
- A stale-source finding means successful source requests have stopped relative
  to their prior cadence; successful empty responses do not trigger it.
- Missing GPU data should remain unavailable on non-NVIDIA hosts.
- A latency regression recommendation requires profiling source and LLM latency
  before increasing concurrency.
- Verify the release/changelog mounts when update messages are missing.
- If a Trivy target fails, inspect `watcher-security-scan`; the other target is
  still attempted and ingested. The scanner runs as the runner UID/GID and its
  cache state uses explicit write mode even for the `workflow_run` trigger.
  Verify the remote report directory is mode `0700`, report files are `0600`,
  and Maintenance listens only on loopback.
- An NVD/OSV outage is isolated and retried on the next daily/manual evaluation;
  it must not resolve or downgrade previously stored findings.
- OpenLIT startup errors usually mean the enabled configuration lacks a valid
  OTLP endpoint/header. Disable it or correct the external collector; do not
  enable prompt capture to troubleshoot transport.
